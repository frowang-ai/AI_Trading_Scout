# 数据获取与存储策略 (Data Strategy)

## 1. 问题背景与约束
- **API 限制**：Tushare 等数据源通常有积分限制和每分钟调用次数限制 (QPS)。
- **计算需求**：因子计算通常需要“过去 N 天”的历史窗口（Time-Series），而数据更新通常是“今日全市场”的切片（Cross-Section）。
- **存储考量**：需平衡磁盘占用与读取速度。

## 2. 数据量级估算 (以 A 股为例)
在制定策略前，我们先进行定量分析：
- **股票数量**：约 5,000 只。
- **时间跨度**：20 年 (约 5,000 个交易日)。
- **日线数据 (Daily)**：
  - 总行数：$5,000 \times 5,000 = 2,500 万行$。
  - 字段数：约 10-15 个 (Open, High, Low, Close, Vol, Amount, etc.)。
  - **存储大小 (Parquet 压缩)**：约 **2GB - 4GB**。
  - **结论**：**日线数据完全可以全量本地存储**，无需担心空间问题。现代硬盘（SSD）读写几个 GB 的数据非常轻松。

## 3. 数据获取策略 (Acquisition Strategy)

### 3.1 历史数据初始化 (Initialization)
- **策略**：**按时间段分批获取**。
- **方法**：虽然我们需要所有股票的历史，但 Tushare 单次返回行数有限制（通常几千行）。
- **执行逻辑**：
  - 遍历过去 20 年的每一个交易日。
  - 对每一天，调用一次 `pro.daily(trade_date='YYYYMMDD')` 获取全市场数据。
  - **优势**：避免了按股票代码循环 5000 次的低效操作，且天然符合数据源的组织方式。

### 3.2 日常增量更新 (Daily Update)
- **策略**：**按日期获取 (Cross-Sectional Fetching)**。
- **执行逻辑**：
  - 每日收盘后，调用 **1 次** API 获取当日全市场行情。
  - 存入“原始数据区 (Raw Layer)”。
- **优势**：极大节省 API 调用次数（1 次 vs 5000 次）。

## 4. 数据存储架构 (Storage Architecture)

为了解决“按日期写入”与“按股票读取计算”的矛盾，我们设计 **Raw (原始层)** 和 **Processed (加工层)** 两层存储结构。

### 4.1 Layer 1: 原始数据层 (Raw Layer / Landing Zone)
- **目的**：最快速度落地 API 数据，作为数据湖。
- **结构**：按**日期**分区。
- **路径示例**：
  ```text
  data/raw/daily/2023/20231101.parquet
  data/raw/daily/2023/20231102.parquet
  ...
  ```
- **特点**：写入极快（Append），但读取某只股票的历史数据很慢（需要打开数千个文件）。

### 4.2 Layer 2: 结构化数据层 (Processed Layer / Serving Zone)
- **目的**：为因子计算提供“按股票索引”的高效读取能力，同时避免产生数千个小文件。
- **结构**：**按股票代码哈希分桶 (Hash Bucketing)**。
- **设计理由**：
  - 单个大文件（2GB+）在需要并行读取多只特定股票时，可能会有锁竞争或内存浪费。
  - 5000 个小文件（每只股票一个）会导致文件系统性能下降（Inode 耗尽、列表慢）。
  - **分桶策略**：将 5000 只股票均匀打散到 50-100 个 Parquet 文件中（每个文件包含约 50-100 只股票的完整历史）。
- **路径示例**：
  ```text
  data/processed/bucket_00.parquet  (包含 000001.SZ, 000050.SZ, ...)
  data/processed/bucket_01.parquet
  ...
  data/processed/bucket_49.parquet
  ```
- **ETL 流程**：
  1. 定期（如每周）读取 Raw Layer 的增量数据。
  2. 将数据按 `hash(ts_code) % 50` 分配到对应的 Bucket 中并重写。

### 4.3 Layer 3: 因子特征层 (Feature/Factor Layer) [新增]
- **目的**：将计算后的因子与原始行情分离，实现“因子资产化”。
- **结构**：与 Processed Layer 保持一致的分桶策略，或按因子类别分表。
- **路径示例**：
  ```text
  data/factors/momentum/bucket_00.parquet
  data/factors/volatility/bucket_00.parquet
  ```
- **元数据管理**：引入 `factors_meta.db` (SQLite) 记录因子定义、版本、依赖关系。

## 5. 计算模式：按股票并行与分块 (Computation Pattern)

针对您提出的“本地按股票并行计算”的需求，我们采用 **“分块并行 (Chunked Parallelism)”** 模式。

### 5.1 每日增量计算 (Daily Update)
**核心痛点**：计算今日因子通常需要过去 N 天的历史（如 MA20 需要前 19 天）。
**解决方案**：**滑动窗口内存切片 (Sliding Window Buffer)**。
1.  **读取**：不读取 20 年历史。仅从 Processed Layer (或缓存) 读取全市场**最近 N+Buffer 天**的数据（例如过去 60 天）。这部分数据量极小（约 50MB），可瞬间加载进内存。
2.  **合并**：将今日刚下载的 Raw 数据拼接到末尾。
3.  **计算**：
    -   利用 `groupby('ts_code')` 将数据逻辑上拆分为单只股票的 DataFrame。
    -   **并行执行**：使用 `multiprocessing` 或 `joblib`，同时处理多个分组（如您所说的“同时拉起四五只股票”）。
    -   *注：对于 Pandas/Polars，直接使用向量化的 `groupby().apply()` 通常比手动多进程更快，但手动多进程对复杂逻辑（如循环迭代）更灵活。*
4.  **写入**：仅将计算好的**今日因子值**追加到因子数据库 (Layer 3)。

### 5.2 全量历史重算 (Full Re-calculation)
**场景**：新因子开发或逻辑修正。
**流程**：
1.  **按 Bucket 迭代**：每次只读入一个 Bucket 文件（约 50-100 只股票，几百 MB）。
2.  **内存计算**：在内存中对这 100 只股票进行并行计算。
3.  **释放内存**：保存结果，释放内存，读取下一个 Bucket。
**优势**：完美解决内存顾虑，同时保持了“按股票处理”的逻辑独立性。

## 6. 总结建议

1.  **放心存储**：日线数据量很小，建议**全量本地存储**，不要删除历史数据。
2.  **按天获取**：API 调用坚持“按交易日获取全市场”的原则。
3.  **分桶存储**：Processed Layer 采用 **Hash Bucketing**，平衡文件数量与读取效率。
4.  **窗口计算**：每日更新时，仅加载“滑动窗口”数据，避免全量加载，实现秒级更新。
5.  **因子分层**：新增 **Layer 3 因子层**，将因子数据独立存储，并引入元数据管理，向专业机构的 Feature Store 架构靠拢。
