# 东方财富多股票 SSE 采集器工程设计

本文定义 `details/sse` 正式采集器的进程模型、容量口径、断线恢复、写盘策略和分阶段验收标准。它面向盘中提醒与研究留档，不把东方财富网页接口视为有 SLA 的授权行情源。

## 一、设计目标与边界

第一阶段目标：

- 同时追踪一组自选股的约 3 秒分笔成交聚合；
- 每 3 秒获取一次行情/五档快照；
- SSE 断线后自动重连，并用 `details/get` 的最近窗口尽力回补；
- 实时提醒不等待磁盘写入；
- 所有断线、回补、去重碰撞、丢弃和队列积压均可审计；
- 单机先支持 10～50 只，实测通过后再逐级放大。

不承诺：

- 交易所严格 Tick 或 Level-2 订单流；
- `details/get` 最近窗口滚过之后仍能恢复；
- 网页接口限流、字段变更或服务端漏发时绝对不丢数据；
- 用 3 秒快照复原两个快照之间发生过的盘口变化。

## 二、推荐进程结构

采用一个 `asyncio` 进程，而不是“一只股票一个线程”：

```text
SymbolRegistry
  ├─ SSE Supervisor（每股一个异步连接任务）
  │    ├─ 解析帧、规范化、连接状态机
  │    └─ 断线时投递 RecoveryJob
  ├─ Quote Scheduler（统一绝对时钟、分散请求尖峰）
  ├─ Recovery Workers（限并发调用 details/get）
  ├─ Alert Engine（内存中立即计算提醒）
  ├─ Bounded Event Queue（有界队列与背压）
  ├─ Single Writer（批量追加 JSONL）
  └─ Metrics / Health Reporter
```

核心原则：

1. 网络任务只负责读取、解析和投递，不直接各自写文件；
2. 一个写入协程集中批量写盘，避免数百个文件句柄和小随机写；
3. 提醒引擎从内存事件流消费，不让磁盘延迟阻塞提醒；
4. 实时 SSE、HTTP 回补和快照使用同一规范化事件模型，但保留 `source_kind`；
5. 所有队列有明确上限，满队列必须告警，不能静默丢弃。

## 三、连接状态机

每只股票独立维护：

```text
STARTING
  -> BACKFILLING（details/get 启动重叠窗口）
  -> CONNECTING
  -> STREAMING
  -> DISCONNECTED
  -> RECOVERING（details/get 回补 + SSE 重连）
  -> STREAMING
```

连接关闭、EOF、socket 错误、HTTP 非 200 才是确定断线。无事件不是确定断线：午休、停牌、收盘和低流动性股票都可能长时间没有成交。

推荐退避为 `1, 2, 4, 8, 15, 30` 秒并加入约 `±20%` 随机抖动。抖动用于避免网络恢复后所有股票同时重连形成“重连风暴”。连接稳定一段时间后才把重试次数清零。

断线恢复顺序：

```text
记录断点
  -> 立即尝试 details/get 回补（不等待 SSE 成功）
  -> 按退避建立 SSE
  -> 对 SSE 首帧和回补窗口统一去重
  -> 回到 STREAMING
```

关键时限不是“60 秒内连回 SSE”，而是缺口滚出最近 20 条之前至少成功完成一次 `details/get` 回补。按每 3 秒一条只能粗略估算为约 60 秒；正式目标设置为断线后 5 秒内发起首次回补、30 秒内成功获得一次窗口。

## 四、多股票的容量模型

设：

```text
N = 股票数
T = 每日连续交易秒数 = 14,400
r = 每股分笔聚合频率，压力估算取 1/3 条/秒
B = 一条规范化 JSONL 大小，本机样例约 423 字节
```

则：

```text
成交事件率        = N / 3 条/秒
每日成交记录数    = N × 4,800 条
每日规范化成交量  = N × 4,800 × B 字节
3秒逐股快照请求率 = N / 3 请求/秒
```

本机诊断结果（100,000 条；批量缓冲写入，每 100 条 flush；不含网络、原始帧和逐条 `fsync`）：

| 股票数 | SSE 长连接 | 成交记录/秒 | 成交记录/日 | 规范化成交 MiB/日 | 逐股快照请求/秒 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 10 | 10 | 3.33 | 48,000 | 19.35 | 3.33 |
| 50 | 50 | 16.67 | 240,000 | 96.74 | 16.67 |
| 100 | 100 | 33.33 | 480,000 | 193.48 | 33.33 |
| 500 | 500 | 166.67 | 2,400,000 | 967.41 | 166.67 |

本机 JSON 编码吞吐约 172,000 条/秒，缓冲写入约 960 MiB/秒。后者主要反映操作系统页缓存，并不代表物理盘逐条持久化能力。与 100 股约 33 条/秒相比，CPU 和顺序写盘不是早期瓶颈。

实际存储预算还要加：

- 原始 SSE 帧（若保留）；
- 每 3 秒行情/五档快照；
- 断线、状态、指标和告警日志；
- 文件系统与 JSON 行尾开销；
- 备份或压缩前的双份数据。

规划磁盘时可先把上表放大 2～4 倍。100 只股票建议暂按每日 `0.4～0.8 GiB` 总量预留，跑满一个交易日后用实测替换该系数。

## 五、真正的瓶颈排序

### 1. 上游连接和请求限制

100 只股票意味着约 100 条 SSE 长连接；若快照仍逐股请求，则另有约 33 次 HTTP 请求/秒。它们比 JSON 编码和写盘更可能先触发连接数限制、502、限流或临时封禁。

尚未验证东方财富是否存在可替代 `stock/get` 的批量五档请求，因此第一阶段不能静默假定可批量。HAR 到位后应优先寻找官方网页实际使用的批量通道。如果只能逐股请求，应：

- 将股票均匀分散在 3 秒窗口内，不在整秒同时发起；
- 使用连接池和 HTTP keep-alive；
- 限制同时在途请求；
- 对 429、502、超时分别计数和告警；
- 扩容按 `10 -> 25 -> 50 -> 100` 阶梯压测，不直接上 500。

### 2. 重连风暴

全局网络闪断会让所有股票同时回补、重连。必须设置全局并发闸门，例如初始限制同时回补 5～10 个、同时建连 10～20 个，并为每只股票加入随机抖动。正常采集与恢复请求应使用不同的并发预算，避免恢复流量压垮快照轮询。

### 3. Python 线程与内存

为每只股票建立 `requests + Thread` 在 100～500 只时会产生大量线程栈、上下文切换和难以控制的关闭行为。正式版使用支持流式响应的异步 HTTP 客户端和单事件循环；按股票数分片仅在连接或故障隔离需要时进行。

异步连接仍会占用 socket、TLS 和接收缓冲。应实测进程 RSS 与打开句柄数，不能只按事件负载估算内存。

### 4. 小写入与强制同步

每条记录独立打开文件或 `fsync` 会把低吞吐事件变成高 IOPS。建议：

- 所有股票按交易日写入一个成交 JSONL 分区，而非每条开关文件；
- 单写入协程按“最多 100 条或最多 200 毫秒”成批写入；
- 普通 `flush` 每批执行，`fsync` 采用 1～5 秒可配置周期；
- 接受突然掉电时最多损失一个 `fsync` 周期，并在元数据中记录持久化水位；
- 若业务要求每条都可抗掉电，再改用 SQLite WAL/专用日志系统并单独压测，不默认逐条 `fsync`。

## 六、数据文件与审计模型

建议按交易日分区：

```text
realtime_alert/data/YYYYMMDD/trades.jsonl
realtime_alert/data/YYYYMMDD/quotes.jsonl
realtime_alert/data/YYYYMMDD/connections.jsonl
realtime_alert/data/YYYYMMDD/collisions.jsonl
realtime_alert/data/YYYYMMDD/checkpoint.json
```

`checkpoint.json` 用临时文件加原子替换更新，不作为逐条事实库；JSONL 才是只追加审计记录。

成交记录至少保留：

```text
schema_version, trade_date, symbol, source_time,
price, volume_lots, trade_count, side_code,
received_at, source_kind, connection_id,
frame_sequence, detail_sequence, full,
recovered, reconnect_attempt, dedupe_key
```

去重索引只保留覆盖 `details/get` 回补窗口所需的近期键，避免内存随全天无限增长；同时把疑似复合键碰撞写入 `collisions.jsonl`，不能静默吞掉。

## 七、背压与降级原则

队列需要同时暴露：当前长度、最大长度、最老事件等待时间、每秒入队/出队数。正常情况下写入能力远高于事件率，队列持续增长通常说明磁盘故障或 writer 异常。

第一版不做静默降级：

- 成交事件队列满：标记采集不完整、告警，并停止宣称数据完整；
- 写盘失败：告警并暂停相应采集分片，不能只在内存无限堆积；
- 快照请求过载：记录失败，不能用旧快照伪装成新快照；
- 回补窗口疑似滚过：产生明确的 `unrecoverable_gap` 审计事件。

提醒事件应带 `data_quality`，在断线或缺口未恢复期间标为 `degraded`，避免用户把不完整输入生成的提醒理解为完整监控结果。

## 八、分阶段实现与验收

### 阶段 A：离线与受控故障（已完成首版）

- [x] 定义事件 schema、状态机和复合去重键；
- [x] 离线验证 SSE 半帧/多行解析、受控断线、重复键和同股回补任务串行化；
- [x] 实现 `details/get` 重叠回补、有限重试和重复审计；
- [x] 验证 writer 按批量/时间写入、优雅退出和 `fsync`；
- [x] 实现有界队列、writer 失败退出、连接/回补/快照/指标错误审计；
- [x] 同日重启时从 `trades.jsonl` 最多32 MiB尾部恢复近期去重键和每股时间水位；末尾半行会显式计数，非末行损坏则拒绝启动。当前不另设可变 checkpoint，JSONL 仍是唯一事实库。

### 阶段 B：10 只股票实盘

- [ ] 连续运行完整上午或下午交易时段；
- [ ] 记录 CPU、RSS、句柄、网络流量、写盘字节和队列水位；
- [ ] 主动切断单连接和全局网络，验证恢复时间与缺口；
- [ ] 验证午休不被误判为逐股断线；
- [ ] 统计 SSE/HTTP 的状态码和错误率。

截至 2026-08-13 盘后，已完成单股15秒实连：一次运行成功收到 SSE 首帧3条、4次快照和两次资源指标；连续短测期间也观察到东方财富临时主动断开，低频原始请求随后恢复 HTTP 200。100股仍必须按部署文档先做3股、10股阶梯短测，不能把程序硬上限理解为上游已验证容量。

### 阶段 C：阶梯扩容

按 `25 -> 50 -> 100` 扩容，每一级至少运行一个完整交易时段。只有在错误率、恢复时间、队列水位和资源使用稳定时进入下一级。500 只不是首版目标；届时应按 50～100 只一分片拆进程，并优先解决批量快照通道与上游授权问题。

## 九、当前建议配置

首版 10～50 只股票：

```text
runtime                    asyncio，单进程
sse_tasks                  每股一个异步任务
quote_interval             3 秒，按股票散列均匀错峰
writer_batch               100 条或 200 毫秒
fsync_interval             2 秒（可配置）
event_queue_max            10,000 条
recovery_concurrency       5
connect_concurrency        10
backoff                    1,2,4,8,15,30 秒 + ±20% 抖动
first_backfill_target      断线后 5 秒内发起
successful_backfill_target 断线后 30 秒内完成一次
```

这些值是安全的首轮工程参数，不是东方财富保证的容量。正式上限要由阶段 B/C 的实盘指标决定。

## 十、容量诊断复现

```powershell
.\.venv\Scripts\python.exe -m realtime_alert._test_sse_capacity `
  --records 100000 --flush-every 100
```

输出：

```text
realtime_alert/_test_sse_capacity.json
```

该诊断只回答本机规范化 JSON 编码和缓冲写盘是否构成数量级瓶颈，不代表东方财富网络容量，也不能替代实盘阶梯压测。
