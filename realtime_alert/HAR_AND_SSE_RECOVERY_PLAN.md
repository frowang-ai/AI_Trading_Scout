# 东方财富 HAR 采集与 SSE 断线恢复计划

本文档记录两个后续任务：定位东方财富五档盘口的真实数据通道，以及把 `details/sse` 从诊断代码升级为可恢复的盘中成交采集器。

## 一、五档盘口 HAR 采集

### 目标

当前已确认：

- `details/sse` 能推送分笔成交聚合；
- `stock/get` 能返回最新价等行情快照；
- `stock/get` 请求参数中包含买卖五档字段，但匿名响应持续省略这些字段；
- 当前没有证据表明存在另一个匿名可用的五档 SSE 或 WebSocket。

下一步应在东方财富网页肉眼明确显示完整五档时导出 HAR，回答：

1. 五档是否仍来自 `stock/get`；
2. 显示五档时是否出现额外的 SSE、WebSocket、XHR、Fetch 或 JSONP 请求；
3. 是否依赖 Cookie、登录状态、用户权限、节点、查询参数或特定请求头；
4. 五档真实刷新频率是多少。

### 建议采集窗口

优先在连续竞价期间采集：

```text
09:35–11:25
13:05–14:50
```

至少选择：

- 蓝色光标 `300058.SZ`；
- 一只沪市高流动性股票；
- 一只深市主板高流动性股票。

### Chrome 操作步骤

1. 打开目标股票行情页。
2. 按 `F12`，进入 `Network`。
3. 勾选 `Preserve log` 和 `Disable cache`。
4. 确认左上角录制按钮为红色。
5. 清空已有请求。
6. 刷新页面，等待五档出现并继续录制 20～30 秒。
7. 点击一次“更多分时成交”等会触发动态请求的入口。
8. 在请求列表中选择 `Save all as HAR with content` / `Export HAR`。
9. 若发现 `wss://` 连接，另外保存或截图其 `Messages`；HAR 不保证包含全部 WebSocket 帧。
10. 若发现 SSE，另外截图 `Headers` 和 `EventStream/Response`；HAR 不保证保存完整的持续流事件。

### 建议文件

```text

realtime_alert/diagnostics/eastmoney_300058_no_levels.har
realtime_alert/diagnostics/eastmoney_<symbol>_five_levels.har
```

HAR 可能包含 Cookie、会话 Token 和用户标识，只能留在本地诊断目录，不得提交 Git 或公开上传。建议先用未登录的无痕窗口采集；只有未登录无法显示五档时才考虑登录采集。

## 二、SSE 为什么断线会丢数据

东方财富 `details/sse` 发送的是增量成交聚合。实测特征：

- 成交记录时间约为 3 秒粒度；
- SSE 网络帧通常约 6～7 秒发送一次，每帧含 2～3 条；
- 首帧 `full=1` 返回少量最近记录；
- 后续帧 `full=0` 返回新增记录；
- 事件没有 `id`，浏览器 `lastEventId` 为空。

如果连接在下面这段时间断开：

```text
13:10:00  已收到
13:10:03  断线期间产生
13:10:06  断线期间产生
13:10:09  重连成功
```

服务器没有可供客户端声明的最后事件序号，也没有已验证的标准重放协议。因此 `13:10:03` 和 `13:10:06` 不一定通过 SSE 自动重新发送。只做“断线后立刻重连”仍可能形成数据缺口。

## 三、推荐恢复流程

### 正常启动

```text
details/get 拉取最近 N 条
  -> 立即持久化并建立去重索引
  -> 建立 details/sse
  -> 首帧与本地数据去重
  -> 持续写入增量事件
```

### 断线恢复

```text
检测到连接 error / EOF / HTTP 失败
  -> 记录 disconnected_at 和最后一条 source_time
  -> 按退避策略重新连接
  -> 重连前或重连后调用 details/get 拉取重叠窗口
  -> 与本地记录去重
  -> 补写未见记录并标记 recovered=true
  -> 恢复消费 SSE
```

推荐初始退避：

```text
1s, 2s, 4s, 8s, 15s, 30s
```

成功连接并稳定收到数据后重置退避。公开接口没有 SLA，持续失败必须告警，不能无限静默重试。

### 去重键

东方财富没有提供唯一成交序号。当前只能使用复合键：

```text
trade_date
+ symbol
+ trade_time
+ price
+ volume_lots
+ trade_count
+ side_code
```

这个键适合网页聚合记录去重，但不是数学上绝对唯一。若未来发现同秒同价同量同笔数同方向的两条合法记录，需要增加接收顺序、帧摘要或上游其他字段，并保留碰撞审计。

### 必须记录的审计字段

```text
source_time          上游成交时间
received_at          本机收到时间
connection_id        SSE 连接编号
frame_sequence       本地帧序号
full                 上游 full 标记
recovered            是否由 details/get 回补
disconnect_started   断线开始时间
reconnect_attempt     第几次重连
dedupe_key            当前复合去重键
```

## 四、不能用“3 秒无消息”判断断线

“成交记录约 3 秒粒度”不等于“服务器每 3 秒必发一帧”。当前实测每帧常间隔约 6～7 秒，而且以下情况会长时间没有新成交事件：

- 午间休市；
- 收盘后；
- 停牌；
- 极低流动性证券；
- 上游将多条记录继续批量发送。

因此：

- 首选以 HTTP 连接关闭、读取 EOF、socket 错误或 EventSource `error` 判定断线；
- 若要增加“疑似僵死”超时，应使用远大于正常帧间隔的阈值，并结合交易时段；
- 超时后先用轻量 HTTP 请求验证网络/数据源，再主动重建连接；
- 不应每逢 3 秒无事件就重连，否则会主动制造连接抖动和限流风险。

## 五、可恢复范围与不能保证的部分

恢复机制不复杂，但只能做到“尽力回补”，不能承诺绝对不漏：

| 场景 | 恢复预期 |
| --- | --- |
| 短暂断线，缺口仍在 `details/get` 最近窗口内 | 大概率可补回 |
| 重连首帧恰好覆盖缺口 | 可通过去重保留新增记录 |
| 长时间断线，最近窗口已滚过缺口 | 可能永久丢失 |
| `details/get` 被限流、502 或代理失败 | 当次无法补回，应重试并告警 |
| 程序崩溃且数据未及时持久化 | 内存中尚未落盘数据可能丢失 |
| 上游本身漏发或聚合 | 客户端无法恢复上游从未提供的数据 |

已实测 `details/get` 的超大窗口（如 `pos=-5000/-10000`）会失败，不能假设它能够事后下载全天成交。因此生产采集必须实时落盘，恢复窗口保持有限且重叠。
